## Summary verdict

This SIMINIT slice is **not the GZCOM boot/service-creation path**. It is the **front-end "new game / load game" flow**: a mode-driven setup-screen builder, its window-message dispatcher, the widget-population helpers, a directory browser, a chunk-tagged grid/scenario file **deserializer**, a GZCOM **property/variant serialization dispatch table**, and text-edit/list-render controls. The highest-value structural finds are the tag→offset deserializer (`FUN_10001ada`), its matching grid accessor (`FUN_10001379`), and the variant serialization jump table (`FUN_10023a27`). The boot ORDER of layer modules is elsewhere; see "Not determined".

All bodies use one recurring string class (vtable `PTR_LAB_1002f230`; ctor `FUN_10002bf3`/`FUN_10004405`/`FUN_10001284`, assign `FUN_1000133f`/`FUN_1000716c`, append `FUN_1000269b`, dtor `FUN_1000228d`) and a localized-text fetch `FUN_100282fc(buf, stringId, groupGuid)` + `FUN_1002835c`. A shared **game-mode selector** lives at `this+8` with six magic values (see notable findings).

## 2. Notable findings (structural)

**Chunk-tag file deserializer + matching accessor (the biggest find).**
- `FUN_10001ada` @ `0x10001ada` reads a chunk-tagged binary stream: 4-byte tag + 4-byte length, **each 32-bit value byte-swapped** by `FUN_10025ef1` (bswap32), i.e. the on-disk format is **big-endian**. Each tag is matched against a table of constants at `&DAT_10037210, 0x10037208, 0x10037200, 0x100371f8, 0x100371f0, 0x100371e8, 0x100371e0, 0x100371d8, 0x100371d0, 0x100371c8 …` down to `0x10037170` (read via `FUN_1000213f`). Matched chunks are copied by `FUN_10002021(stream, len, dest, cap)` into a fixed struct layout and OR-in presence bitflags at `this+8/+9/+10`. [CONFIRMED @ 0x10001ada]
- `FUN_10001379` @ `0x10001379` is the **read accessor** for the same struct: layer id → (base offset, stride). Three grid resolutions are proven by the stride constants: **128×128** (stride 0x80, layers 1/2/4/8/0x10/0x20 at this+0x1000c/0xc00c/0x1c00c/0x1800c/0x1400c/0x800c), **64×64** (stride 0x40, layers 0x40/0x80/0x100/0x200), **32×32** (stride 0x20, layers 0x400/0x800/0x1000/0x2000/0x2000c). [CONFIRMED @ 0x10001379] This offset map is the authoritative struct for that file format.

**GZCOM variant/property deserialization jump table.**
- `FUN_10023a27` @ `0x10023a27` is a full type-tag dispatch reading a variant object: type `0`=void, `1..0xc`=scalar getters (bool/int16/int32/int32×2/uint8/uint16/uint32/uint32×2/float/double/…), `0x7fff`=nested object, `0x8000..0x800f`=array/blob variants. Each case reads via one vtable slot on the source and writes via the paired slot on `this`. This is the serialization primitive to reuse when parsing any GZCOM persistent record. [CONFIRMED @ 0x10023a27]

**Setup-screen build + message-pump pair (front-end entry).**
- `FUN_1000ffda` @ `0x1000ffda` builds the entire "new game / load" screen; `FUN_1000f82a` @ `0x1000f82a` is its window-message dispatcher. `FUN_1000f82a` routes three top-level message classes: `param_2==0xa2bf8ace → FUN_1000ffda` (rebuild), `0xa2bf8acf → FUN_10013773`, `0xa2bf8ad0 → FUN_100137a4`; class 3 = widget notifications; class 5 = commands. [CONFIRMED @ 0x1000f82a]

**Game-mode selector (recurs across 11 of the 25).** Field `*(this+8)` holds one of six content-mode magics; `FUN_10012c9f` decodes three of them to directory names, establishing their meaning:
- `0x63172b74` → `"StarterTowns"`
- `0x23172af2` → `"Terrains"`
- `0xA42C7725` (`-0x5bd388db`) → `"Scenarios"`
- default (incl. `0x83172AD7`/`-0x7ce8d529`) → `"Cities"`
- `0xBA2547AE` (`-0x45dab852`), `0xC3172AEA` (`-0x3ce8d516`) also branched but not name-mapped here. [CONFIRMED @ 0x10012c9f]

**Widget-id block.** The setup dialog uses a contiguous control-id range `0x2dfdd6a … 0x2dfdd81` (OK button `0x2dfdd6a`, dir combo `0x2dfdd6c`, list `0x2dfdd6e`, tree/list source `0x2dfdd6f`, label fields `0x2dfdd70..74`, thumbnails `0x2dfdd75/76`, checkbox `0x2dfdd7b`). Common interface IIDs seen: `0x212cdc1f` (label/setText), `0x21335c59` (selection list), `0x4132242b` (item list), `0x412ce496` (tree). [CONFIRMED across 0x1000ffda, 0x1001515b, 0x100158e9, 0x10015d17, 0x1001613c, 0x10014e1f, 0x100137ca]

**Localized-text resource fetch (tunable-ish).** `FUN_100282fc(buf, stringId, groupGuid)` + `FUN_1002835c` is the string-table lookup used everywhere. Distinct group GUIDs act as string-table namespaces: `0x29541f4`, `0x41f2625`, `0x15e410c`, `0x209e6378`. Not a numeric tunable table, but the closest thing to a named-key table in this slice. [CONFIRMED @ 0x1000ffda et al.]

## 3. Not determined

- **The GZCOM service getters themselves.** Functions `FUN_100298b6` (sim/active-city mgr — vtbl 0x88/0x78/0x17c/0x15c/0x1e4/0x234/0x238/0x21c/0x220), `FUN_1002062f`/`FUN_10020603` (graphics/color+font — makeColorRGB @ vtbl+0x84), `FUN_1002065b` (window/msgbox mgr), `FUN_1001fe49`/`FUN_1002997f` (GZCOM class factories, `CreateInstance` @ vtbl+0xc), `FUN_100299ab` (message pump, post @ vtbl+0x14), `FUN_100299f7` (settings), `FUN_100205ab` (region/tract map), `FUN_100206b3`/`FUN_100206df` (path/locale), `FUN_1002985b` (doc service) are **called but not in this slice**. Their concrete class identity (which is what the boot-order task wants) cannot be fixed from these call sites alone. Missing evidence: the bodies of those getters (do they lazily create vs. look up a registered singleton?) and the module-level init routine that first registers them. Recommend targeting those RVAs next.
- **`FUN_10001ada` tag→meaning.** The 18 tag constants at `DAT_10037170..10037210` were read as pointers, not dereferenced; the literal 4-char tag strings/values behind them were not resolved here. Missing evidence: the byte contents at those `.data` addresses (grep `globals.csv`/`strings.csv` for `0x10037170`–`0x10037210`), needed to name each grid layer.
- **Exact file-format identity for the `FUN_10001ada`/`FUN_10001379` struct** (scenario `.scn` vs. terrain vs. tutorial). The offsets and big-endian chunking are confirmed, but which on-disk file drives it is not shown in the slice.
- **iOS cross-check not performed on this slice.** Several patterns (variant dispatch, chunk loader) plausibly map to `cIGZVariant`/`cGZPersistDBRecord`-style code in the unstripped iOS binary, but per project rules struct offsets do not transfer and I did not open `ghidra_export_ios`; I am not asserting any `[iOS-HINT]` name without a second witness.

All 25 functions in the slice were read and classified at C2 (body read, callees identified, mechanically described, named). None are rated C3/C4 — that requires runtime or a second witness, which this read-only pass cannot produce.
