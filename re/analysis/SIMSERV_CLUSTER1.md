## 2. Notable findings (structural)

- **A complete INI / tuning-config access layer (7 functions).** `this+0xb4` is a *config-source type* selector set lazily by **`sc3_serv_init_config_source` (0x10017287)** to `1` (std::map-indexed INI, `this+0x1c` section map + `this+0x28`/`this+0x78` stream) or `2` (PAK-style bracketed section, delimiters `DAT_1002470c`/`DAT_10024708`). Two dispatch fronts sit on top: **`sc3_serv_lookup_config_entry` (0x10016c11)** for one key and **`sc3_serv_enum_config_entries` (0x10016f08)** for all keys. Backends are **`sc3_serv_read_ini_value` (0x10011dbb)**, **`sc3_serv_enum_ini_section` (0x10012058)**, and the writer **`sc3_serv_write_ini_stream` (0x1001146d)**. The write formats are literal: `"[%s]\n"` / `"%s = %s\n"` / `"\n[%s]\n"` `[CONFIRMED @ 0x10024670/0x10024664/0x10024658]`. This is the machinery that reads `SC3*.INI` `[TuningParameters]` — i.e. the read path for every tunable named in the module map §4, and it round-trips (write path present).

- **A save/serialiser object is created per layer.** `sc3_serv_layer_init_spread` (0x10006aca) does `operator_new(0xf0)` into `this+0xa8` then calls its `+0x4c`/`+0x50`/`+0x54`(0x43092c78)/`+0x58`(0x83092c7f)/`+0x5c` — the GZCOM stream-writer primitive set documented in the sibling SIMGEOM/SIMDSTR work. This is the per-tick layer's persistence hook.

- **A spread/decay tick — a second, independent copy of the fire-spread algorithm.** `sc3_serv_spread_tick` (0x1000fa07) is structurally identical to the documented fire tick `0x1000b6f7` but on its own globals: ignition `rand(FUN_100134fc,10000) < value` → posts message **`0x632e2ad6`** to scheduler `0x1001325b`; extinguish at `MaxStrikeDuration=DAT_10024550` or heat `+0xd0 >= 100`; heat scaled by `StrikeEfficiency=DAT_1002454e/100`; 16-cell time-sliced scan with phase step tables **`DAT_10024558`/`DAT_1002455c`** (the police/crime analog of fire's `DAT_100243d0/d4`); burn/coverage stats accumulate at `+0xdc/+0xe0/+0xe4`.

- **The police/crime coverage cluster mirrors fire 1:1.** Radial brush **`sc3_serv_stamp_coverage_radial` (0x1000f557)** is the exact analog of fire `0x1000b36a` (same `floor(sqrt)+_DAT_1001e3c8` distance, center→edge lerp, `/0x10`, clamp `0..0xff`) with its own effect/radius tunables `DAT_1002453a`/`DAT_1002453b` and scale `DAT_10024540`. Add-agent **`sc3_serv_add_dispatch_agent` (0x1000e981)** is the analog of fire `0x1000a9c6` — **same `0x2c`-byte agent object and the same three vtables `PTR_FUN_1001f0ec`/`1f0bc`/`1ef74`**, message header `0x207edc0e` with suffix `0x32cb` (fire uses `0x32cc`), IID `0xc14f8955`, notification `(1,0x22,…)` (fire uses `0x23`). Building handlers, init, and shutdown round out the cluster.

- **A global building-modifier table `DAT_10024968`.** Loaded line-by-line by `sc3_serv_load_building_modifier` (0x1000689e) as `buildingId → {radius, signed effect [-127,127]}` and consumed by `sc3_serv_stamp_building_modifier` (0x10007d35), which stamps that signed effect over a grid when a building is placed/removed. This matches the shape of the crime `AgentIDModifiers` tunable named in module map §4 (per-building crime deltas).

- **New tunable globals surfaced (parse targets; values live in the data files, not the binary):** `DAT_100242d4` (cells/tick divisor, `w*h/(DAT_100242d4*4)`), `DAT_1002453a` (dispatch effect), `DAT_1002453b` (dispatch radius), `DAT_10024540` (coverage scale), `DAT_1002454e` (StrikeEfficiency), `DAT_10024550` (MaxStrikeDuration), `DAT_1002429c/d/e` + `DAT_100242ac` (query radius + thresholds), `DAT_100240d0/d4` (station query radius/divisor). Message/notification ids: `0x632e2ad6` (ignition), `(1,0x22,…)` (dispatch notify). New GZCLSID/IID edges: `0xc144aca9→0x2144802b`, `0x0259c03f→0x4259c018`, `0x810d4d90`, `0x42ee7a62`, `0xe0faadc7`, `0x80ffe58e`, registry keys `0x32ca`/`0x334a`/`0x3639`.
