## 2. Notable findings (structural)

**A. The RCI/valve layer save↔load serialiser PAIR — `0x10022169` (save) + `0x10021cf3` (load).** The most valuable find in the slice, and directly answers the task's "any serialiser pair". Both key the same persistent record `{0x206c6e7c, 0xc106c4f5}` and use the same stream interface (obtained via `FUN_1003ff09`), with symmetric primitives: **read** `+0x18` (byte/bool) / `+0x38` (short) / `+0x3c` (block); **write** `+0x68` (bool) / `+0x88` (object) / `+0x8c` (array, capacity `0x5a`). Both touch the identical field set: bools `this+0x640/0x641/0x642`, the 4 sub-objects at `this+0x74/0x1dc/0x344/0x4ac` (stride `0x168`=360), the accumulator objects `this+0x644..0x67c`, and the 3 demand gauges `this+0x680/0x684/0x688`. This is the on-disk shape of the RCI demand layer in the city save.

**B. The demand-accounting core — census + init + refresh, now connected.** Three functions form the live RCI demand loop:
- `0x10021165` **`sc3_rci_layer_init`** creates the census manager (`operator_new(0x50)`→`FUN_10025c91` at `this+0x14`), subscribes **message `0xbb9`**, builds the demand graph via `FUN_100214e0` (CLUSTER1's `sc3_rci_init_demand_graph`, called on `this-0x10`), and zeros exactly the fields that (A) serialises.
- `0x10025759` **`sc3_rci_census_update_building`** is the add(`mode 0`)/remove(`mode 1`) that maintains two running totals (`this+0x628`, `this+0x640`) partitioned into 3 wealth tiers each (`+0x634/0x638/0x63c`, `+0x64c`), keyed off building type `+0xc`, and pushes each total to a gauge (`+0x630`/`+0x648` vtable `+0x18`). GZCLSIDs `0xe0faadc7` (zone), `0x62ae25ad`, `0x42ebdb49`, `0xa2eab10d`.
- `0x100225c3` **`sc3_rci_graph_refresh_labels`** repaints 3 gauges × 3 series. **This corrects CLUSTER1**, which listed `FUN_100225c3` only as an opaque "tail of `sc3_res_simulate_population`" — it is the demand-display refresh called after the sim math, and it confirms gauges at layer `+0x690/+0x694/+0x698` with label sources `+0x69c/+0x6b0/+0x6c4`.

The offset reconciliation is clean: `sc3_rci_init_demand_graph` (CLUSTER1) stores gauges at `layer+0x690/694/698`; here they appear at `this+0x680/684/688` because init/census/serialise run on `this = layer-0x10`. Same three objects.

**C. Demand-curve data loader — `0x1001c204` `sc3_rci_load_demand_curve`.** A `char`-dispatched (`'r'`/`'c'`/`'i'`) parser that loads per-type curves (values scaled `×1000`) into three maps `DAT_10058678`(res)/`DAT_10058668`(com)/`DAT_10058658`(ind), sets loaded-flags `DAT_1005867c/6c/5c`, and writes defaults into `DAT_100579a8/a9/aa` — the same Res/Com/Ind land-value city-center-effect globals CLUSTER1 attributed to `sc3_landvalue_load_tuning`. A modding-facing data table.

**D. The R/C/I building growth-table loaders — `0x10017649` (ind) / `0x10028864` (res) / `0x1000f6d8` (com).** Three near-identical data-file parsers (`FUN_10036fc1` tokeniser, delimiters `DAT_100574c4/10057624/10057628`) that read one growth-table record per line — `{id, value, category, level}` — track a min/max level range, and hand each row to a per-type sink (`FUN_10017c02`/`FUN_10028ce0`/`FUN_1000fb21`). The industrial one additionally classifies a leading char `'A'→2 / 'C'→0 / else→1`. These define which buildings appear at which density/wealth level, and complete the R/C/I developer picture from CLUSTER1 (ctors + evaluators + placers + **now the growth tables**).

**E. Two more config ctors + one civic pair extend the tunable map.** `0x10006416` `[Hospital]`→`DAT_100573c4..d8`, `0x1000793d` `[Library]`→`DAT_1005741c..28`, `0x10008aae` `[Museum]`→`DAT_1005745c..68` — all in `\Sys\SC3Tune.INI` / `SYS.PAK`, same idiom as CLUSTER1's School/College. **F. **G. - **`0x1001c204` (`sc3_rci_load_demand_curve`) — curve axis.** The map key (`local_18`) and what the `×1000` value represents (demand cap vs. a parameter axis) are not determinable from the body; I describe it as scaled keyed inserts. - **`0x10025759` channels A/B identity.** The two totals (`this+0x628`, `this+0x640`) with 3 wealth tiers each are clearly two RCI channels, but which is R vs C vs I is not proven from this body (the GZCLSIDs `0x62ae25ad`/`0x42ebdb49` are unresolved).
