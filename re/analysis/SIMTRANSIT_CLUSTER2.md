### 2. Notable / structural findings

**★ Message dispatcher + sim wiring — the per-event entry the task asked for.**
- `FUN_10005830` `sc3_transit_dispatch_message` `[@0x10005830]` is the layer's **top message handler**. It routes the four subscribed sim messages to the network-grid maintainers already named in CLUSTER1: occupant-added `0x2bdf19f`/`0x826cb9b6` → `FUN_10005983` (net-stamp), occupant-removed `0x12bdf19f`/`0x426cb9b3` → `FUN_10005eb1` (net-clear), each with an occupant-type selector (`0x51c4bf8e` or `0x1787abd`). It also handles command `0x230e27ac` carrying arg id `0x837961ea` (`traffic_lights`, from CLUSTER1's Init).
- `FUN_10003d93` `sc3_transit_register_sim` `[@0x10003d93]` is the **registration** that makes the above live: it subscribes exactly those four message ids (`0x826cb9b6 / 0x426cb9b3 / 0x2bdf19f / 0x12bdf19f`), and calls `FUN_100087fd` to load tunables. **This closes the "per-tick callback" question for the occupant/network-maintenance path** — the messages are event-driven (occupant add/remove), not a bare per-tick Simulate. No pure per-tick `Simulate` still appears in this slice.

**★ Network-to-TRANSIT boundary — the consumer side, now found.**
- `FUN_10003d93` acquires the two **network sub-layer interfaces `0x8290f605` and `0xc290f609`** into `this+0xe8/+0xec` (alongside `+0xf0/+0xf4` from CLUSTER1's Init). These are what SimTransit holds the network through.
- `FUN_10008a94` `sc3_transit_query_reachable` `[@0x10008a94]` is the **network-consumer read**: it tests the ushort network-flag grid `this+0x5c`, specifically **bit `0x400` = "connected"** (the same connectivity bit `FUN_10005983` OR-sets per CLUSTER1) for road type, and shifts for rail/other. This is the transit side reading network connectivity per cell/type. The actual expansion still runs through CLUSTER1's `FUN_1000755e`/`FUN_10008642`, whose scan order is set up by `FUN_10008485` (below).

**★ Pathfinding scan-order iterator.**
- `FUN_10008485` `sc3_transit_init_cell_scan_order` `[@0x10008485]` sets up grid traversal: either an explicit packed-coord list (`this+0x20`), or a **pseudo-random coprime-stride walk** — bucket by area against thresholds `DAT_1001a2d6/2ea/2fe/312/326/33a`, coprime stride from table `&DAT_1001a2c4` → `this+0x34`, random start `rand()%count` → `this+0x30`. This is the origin-scan setup feeding CLUSTER1's `FUN_10008642` "next" iterator.

**★ Serialisers — SimTransit's save section is confirmed on BOTH sides.**
- `FUN_10004c8d` `sc3_transit_save_state` `[@0x10004c8d]` is the **write/save** counterpart to CLUSTER1's load `FUN_100048ee`: same **magic `0x206c6e7c` + group `0x29ca804`**, serialising the byte cost grids `+0x60/64/68/6c/70/74` and the 0x14-grids `+0x7c/80`. So SimTransit **does own a save section — type `0x206c6e7c`, group id `0x29ca804`** (a first for this module, matching the four literals the task listed: `0x206c6e7c`).
- `FUN_10016670` / `FUN_100164d7` are a **write/read descriptor pair** (IID `0x80199683`) serialising a config object (packed 24-bit fields written `>>8` / read `<<8`, plus 3 floats).
- `FUN_10014318` `sc3_transit_record_stream_open` is the record-stream ctor both serialisers ride on — validates header magic **`0xDEADBEEF`** at `+0x8`, reads a 3-u32 (type/group/instance) key.

**★ Tunables + ordinances.** `FUN_100087fd` `[@0x100087fd]` is the trip-tunable refresh: base keys `DAT_1001f0ba..f0cd`, `f10c/110/114` into `this+0xc4..+0xd4`, then **two ordinance modifiers `0xa2bf1de5`** (adds `DAT_1001f0ea` to the four road-distance/coverage radii) and **`0xc2d1b025`** (boosts mass-transit chance `+0xc9` by `DAT_1001f0e8`, scales floats by `DAT_1001f0e9*_DAT_1001a514`).
